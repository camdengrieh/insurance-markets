## 0. Bottom line

1. **The earlier blanket conclusion ("each venue forces its own account type, so a generic derived smart account is wrong for most venues") is half right and half out of date.** It is right for XO (Kernel v3.1 only), Polymarket (Deposit Wallet through Polymarket's own factory and SDK), Limitless (its own Safe or EOA), Probable (proxy wallet) and the two non-EVM venues (Hyperliquid HyperCore API, Pascal). It is wrong, or at least not proven, for four BNB-chain and Base venues where **the settlement contract itself accepts any ERC-1271 or Safe contract maker**: Predict.fun (all four exchange contracts use OpenZeppelin `SignatureChecker`, H), Opinion (any Gnosis Safe whose owner EOA signs, H), Myriad (OpenZeppelin `SignatureChecker` on `order.trader`, H) and Polymarket's own exchange (a generic `POLY_1271` type, H, but the official SDK only wires up its Deposit Wallet). Whether each venue's **off-chain gateway** accepts a smart account it did not provision is the unknown that decides everything and is **NOT ESTABLISHABLE without a live test** for all of them.
2. **The most important new fact: Predict.fun's "Smart Wallet" is the same Kernel v3.1 account that XO forces.** The official SDK (`@predictdotfun/sdk@1.3.8`) hard-codes Kernel implementation `0xBAC849bB641841b44E965fB01A4Bf5F074f84b4D`, ECDSA validator `0x845ADb2C711129d4f3966735eD98a9F09fC4cE57` and the Kernel wrap domain `Kernel`/`0.3.1` (H, `dist/Constants.js`). These are byte-for-byte the XO values in [25] and the XO docs. The SDK's `OrderBuilder.make(chain, signer, {predictAccount})` accepts **any** `predictAccount` address and only checks that `ECDSAValidator.ecdsaValidatorStorage(predictAccount) == signer` (H, `dist/OrderBuilder.js` lines 98 to 107). So one Kernel v3.1 derivation function, owner = a PayBox EOA, is a candidate trading account on **XO (3223), Predict.fun (BNB 56) and Base**, with the same address if the factory call and salt are the same (M, unverified, test T-V1).
3. **Candide's stack fits Safe, not Kernel, and the Safe is the PayBox-friendly flavour.** A Candide Safe signs UserOps as EIP-712 `SafeOp` typed data and ERC-1271 messages as EIP-712 `SafeMessage` typed data (H, `Safe4337Module.sol`, which inherits `CompatibilityFallbackHandler`). PayBox's only no-server route (WalletConnect) signs exactly typed data on ten EVM chains (1, 10, 56, 137, 999, 4663, 5042, 8453, 42161, 43114) and refuses raw digests and transactions ([PW] §1, H[B]). A Kernel **UserOp** hash is a bare 32-byte digest that needs the `raw` intent, so a PayBox-owned Kernel can sign **orders** (1271 wraps are typed data) but not its own UserOps through WalletConnect. The reverse holds at venue level: **Opinion needs a Safe, XO needs a Kernel, Predict.fun natively runs a Kernel.** There is no single smart-account family that every venue accepts.
4. **Candide does not reach XO.** XO (3223) is not in Candide's supported-network list (H), and the Safe singleton, SafeL2, proxy factory, fallback handler and MultiSend are all absent from chain 3223 (XO explorer returned 404 for each while the positive controls returned 200, H, section 4.1). A Candide Safe on XO would need a stack of deployments by a party with no native XO.
5. **"Gasless" is not free and "seamless cross-chain bet placement" does not exist at any venue.** Candide's public bundler/paymaster is keyless but rate-limited per IP, and mainnet sponsorship needs a funded gas policy (someone deposits native tokens and, past an included allowance, pays a per-operation fee); the free Starter plan is 2,500 mainnet UserOps in total on 2 mainnet chains with 1,000 sponsored operations, once (H, candide.dev/pricing, docs.candide.dev). Alternatively the user pays gas in USDT/USDC through Candide's ERC-20 paymaster on BNB, Polygon, Base and Arbitrum (H, token list). Most of the venues in this document already sponsor order and settlement gas themselves (Polymarket relayer, Opinion, Predict.fun, XO paymaster), so Candide's paymaster only adds value on the **on-chain** legs (approvals, deposits, redemptions, Trueo, Pancake, HyperEVM). Candide's "chain abstraction" (Safe Unified Account) means one signature for the same admin change or a USDC/USDT consolidation on many chains, on EntryPoint v0.9; it places no bets (section 6).
6. **On-chain session policies still cannot cap off-chain-signed CLOB orders** (re-tested, section 5.2): the venue calls `isValidSignature(hash, sig)` on the maker and no shipped Safe or Kernel module decodes order content; Candide's own Safe Policies product is "Planned" (H); Candide's shipped delegation for a Safe is the Allowance Module, which limits **token transfers** only. The honest on-chain bounds remain the funded balance, a capped approval, and venue-native delegates (Polymarket Session Keys, Hyperliquid agent wallets, Pascal trading keys, Limitless scoped tokens).
7. **One earlier statement is wrong as written and is corrected here:** [25] §4.1 says PancakeSwap prediction "rejects contract callers outright ... no smart account can bet there". True only for the BNBUSD contract. The BTCUSD and ETHUSD contracts deployed in 2025 carry no `notContract` check (Sourcify `exact_match`, H, section 4.9). They are tiny (about $0.32M per day in total across the three, [venue note]), so this changes little in practice, but it changes the rule "never put a smart account in front of Pancake".
8. **What to build first** (section 7): nothing generic. First the **cheap acceptance tests** on the two venues where the contract says yes and the gateway is unknown (Predict.fun with a PayBox-owned Kernel v3.1; Opinion with a user-made Safe), each costing a $1 to $5 test order the user chooses to make; then, only if they pass, one `AccountProvider` interface with exactly two implementations (Kernel v3.1 for XO and Predict.fun, Safe 1.4.1 for Opinion and the on-chain venues), both owner-derived, both flag-gated OFF, both with the PayBox EOA as the only owner.

### 4.8 Pascal (Solana): not possible for EVM AA

- **Facts (H, `docs.pascal.trade/llms/general.txt`, `request-signing.txt`, [census] entry, re-verified in part):** Solana-only, USDC held in program-owned accounts; the owner wallet signs register/revoke/withdraw actions with plain Ed25519 over UTF-8 JSON; orders are signed by up to 10 registered Ed25519 trading keys over a compact binary permit, expiry at most 365 days, cannot withdraw; sign-up is a Solana wallet or an email in the app; restricted jurisdictions include the US, UK and others ([census]); the ToS prohibits automated means "not provided by us" but Pascal provides a public API and quickstart.
- **Verdict:** an EVM Safe or Kernel cannot produce an Ed25519 signature, so there is no EVM-AA path. The Pascal trading key is the venue-native session key and the owner is a Solana keypair (PayBox Solana credential, a separate key family). Cross-chain funding means a swap/bridge into Solana USDC by the user, not by AA.

### 4.9 PancakeSwap prediction (BNB Chain): correction to [25]

- **Source read (H, Sourcify, `PancakePredictionV2`):**
  - BNBUSD `0x18B2A687610328590Bc8F2e5fEdDe3b582A49cdA` (2021, partial `match`): `modifier notContract() { require(!_isContract(msg.sender), "Contract not allowed"); require(msg.sender == tx.origin, "Proxy contract not allowed"); }` applied to `betBear`, `betBull`, `claim`.
  - BTCUSD `0x48781a7d35f6137a9135Bbb984AF65fd6AB25618` and ETHUSD `0x7451F994A8D510CBCB46cF57D50F31F188Ff58F5` (2025, `exact_match`, Solidity 0.8.26, Ownable2Step, transient reentrancy guard): `betBear`, `betBull`, `claim` are `whenNotPaused nonReentrant` only; the only `msg.sender` requires are admin/operator/keeper roles and "Can only bet once per round"; `extcodesize` appears only inside OpenZeppelin `SafeERC20`; claims pay through `_transferETHAndWrapIfFailWithGasLimit(msg.sender, reward)` (native BNB with a gas limit, wrapping to WBNB if the send fails).
- **Consequence:** a Safe or any 4337 account **can** bet and claim on BTCUSD and ETHUSD. Not on BNBUSD (the largest). [25] §4.1's "no smart account, and no 7702-delegated EOA, can bet there" is true only for BNBUSD. A 7702-delegated EOA would also fail BNBUSD's `msg.sender == tx.origin`? No: for a 7702 EOA, `msg.sender` equals `tx.origin` but `_isContract(msg.sender)` is true (code present), so it still fails (M, reasoned from `extcodesize` semantics, not tested).
- **Economics (from the venue note, H at the time):** about $0.32M staked per day across all three markets, 3% rake, pari-mutuel with unknowable odds until close, basis risk against any hedge. P2 priority stands; this finding only widens what a smart account may do.
- **Verdict:** BNBUSD **not possible**; BTCUSD and ETHUSD **DSA-OK**.

### 4.10 Probable (BNB Chain): venue-forced proxy

- **Facts:** the app asks the user to "create a proxy wallet" on first deposit ("gas fees ... sponsored by Probable"; "the proxy wallet address won't be same as your connected wallet"); the OpenAPI shape in `pmxt-dev/pmxt` (third-party, M) has `maker` "Proxy wallet address or EOA", `signer` "EOA address", an integer `signatureType`, and header auth `prob_address`, `prob_signature`, `prob_api_key`, `prob_passphrase`, `prob_timestamp`, `prob_nonce`. The exchange contract address was not located (NOT FOUND, searched: docs llms index, funding page, OpenAPI file), so contract-level behaviour is unread.
- **Verdict:** **venue-forced (proxy wallet) with an EOA signer**; no smart-account path found; dead volume ([09] §2.5).

### 4.11 Myriad (BNB Chain and others)

- **Contract (H, Sourcify `exact_match`):** the order-book exchange `0xa0b6f8ef8EdB64f395018D1933f2273Ce9f0f16A` is an ERC-1967 proxy whose implementation `0xAaC2a7f99F3F42e99612A1a684384E9c759f8FdA` (`MyriadCTFExchange`) reads `if (!SignatureChecker.isValidSignatureNow(order.trader, orderHash, signature)) revert InvalidSignature();` (line 638). - **Verdict:** **DSA-OK at contract level, gateway unverified**; irrelevant until volume exists.

### 5.2 "On-chain session policies cannot cap off-chain-signed CLOB orders"

Still true, with the mechanism made precise:

- The venue's exchange calls `isValidSignature(orderHash, signature)` on the maker at settlement; the account sees an opaque 32-byte hash (Predict.fun, XO, Myriad, Limitless type 3) or, for Polymarket's Deposit Wallet, an ERC-7739 `TypedDataSign` wrap that **does** include the order contents (H, docs: "ERC-7739-wrapped signature"). In principle an account module could decode the contents and cap price or size; **no deployed module does** (ZeroDev policies list in [25] §6.1; Candide Safe Policies "Planned"; Safe Allowance Module: transfers only) and writing one is barred.
- A Safe session delegate with Allowance Module can only pull ERC-20s out of the Safe, which bounds what a compromised key can **withdraw**, not what an order can lose at the venue. Venue custody (Opinion Safe, Predict Kernel, Polymarket Deposit Wallet) is not the Allowance Module's concern: the CTF exchange is already an approved spender of the account's collateral, so an off-chain order signature can spend up to the approved amount.
- Therefore the on-chain bounds that exist today are: (1) the funded balance of the account; (2) a capped ERC-20 approval to the exchange (Opinion's "Enable Trading" approves the exchange; the SDK's amount is not stated, so a user-sized approval is a test, not a fact); (3) venue-native delegates that are not account modules: Polymarket Session Keys (venue-scoped, cannot withdraw, no amount limit found), Hyperliquid agent wallets (sign only, pruned), Pascal trading keys, Limitless scoped tokens (scopes: trading, account creation, delegated signing).

### 5.3 "PayBox signs typed data on ten EVM chains (not 3223) and cannot sign raw digests through WalletConnect"

Re-checked against the repo's own H[B] reading ([PW] §1, C12): unchanged and consistent with the PayBox docs (typed data and `raw` are separate intents; the `raw` intent exists in the hosted/SDK surface, not in WalletConnect). New implication (section 2.2): the Safe is typed-data native, so the AA family that works on the no-server route is the Safe; Kernel orders work, Kernel UserOps do not.

## 7. What to build first (ordered; everything flag-gated OFF, nothing authored on-chain)

1. **Acceptance tests before any account code (user-run, optional, small).** They are the only way to resolve the gateway question, cost a few dollars and need no contact with anyone:
   - **T-V2 (Predict.fun):** PayBox EOA as owner of a new Kernel v3.1 account on BNB (`initData`: ECDSA validator, owner = PayBox EOA, no hook), deposit about 5 USDT, request an API key in the Developer Console, run the `getAuthJWT` flow with the Kernel wrap, place a 1 USDT limit order far from the market, cancel it. Pass = the gateway accepts a Kernel account it did not provision. The approvals are owner-EOA transactions to `Kernel.execute` (BNB gas).
   - **T-V3 (Opinion):** a Candide Safe on BNB owned by the PayBox EOA; sign an `OpinionApiKeyAuth` with the EOA; observe whether the API rejects the key request because no Opinion trading wallet exists for that address (expected, by the documented prerequisite) and whether any documented route attaches an existing Safe. If no route exists the test is over at zero cost and Opinion stays "venue-created Safe, owner = PayBox EOA", which still allows the PayBox EOA to be the signer.
   - **T-V1 (address identity):** compute the Kernel v3.1 address for one owner with the XO formula ([19] §5) and with the ZeroDev default; compare with a Predict deposit address if the user has one; read-only code queries by the user on 3223, 56 and 8453 confirm factory presence.
   - **T-V4 (PayBox + Safe):** with a throwaway credential, check that PayBox signs a `SafeOp` typed data with the module as `verifyingContract` on chain 56 and chain 8453 (zero value), and that WalletConnect accepts the domain. (Never run; [25] T-AA1 covers the Kernel half.)
2. **If T-V2 passes:** one derive function for the Kernel v3.1 account and one registry row per chain (`derivation: "factory-pure-function"`), reused for XO and Predict.fun; the existing XO UserOp templates and golden vectors ([21], [19]) cover the account; the new work is the Predict JWT and order adapter (the SDK source is MIT and can be read, not vendored without review).
3. **If T-V3 shows a Safe can serve Opinion:** a Safe 1.4.1 derive function (Candide's `SafeAccountV0_3_0.initializeNewAccount([owner])` is the reference; AbstractionKit is MIT with two small dependencies) and an Opinion order adapter that signs the order digest with the owner EOA.
4. **On-chain-only venues (Trueo, Pancake BTC/ETH, Hyperliquid HyperEVM) are not blocked by any gateway**, so they can be done without waiting on tests, using the Safe for batched approve-and-act. They are also the three smallest by volume ([11], venue note), so build only if the batching is valuable to the user.
5. **Do not build:** a bridge, a paymaster, a policy module, a "universal" account abstraction layer that hides the account type, a 7702 delegation, anything on 3223 beyond XO's own Kernel path, or any hosted service that sponsors gas for strangers.
