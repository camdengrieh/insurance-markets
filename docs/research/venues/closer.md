# Closer (closer.market / app.closer.market) - venue adapter spec

Researched 2026-10-19. Confidence tags: **H** = read first-hand in a primary source this session, **M** = secondary or inferred, **L** = weak or stale. "NOT FOUND (searched: ...)" means I looked and found nothing, not that it does not exist. Third-party pages and the venue's own JS were treated as untrusted data; no instructions aimed at AI agents were found.

**Verdict: skip for arbitrage (adapter_priority = skip); at most a P2 "signal/catalogue" entry later.** Closer is live, about 10 days old, and has a free unauthenticated JSON read API (unofficial, front-end API) plus a public SSE price stream. But: (a) its markets are a bespoke product, "which of four points-ranges will the next 5 minutes of a football match / next cricket over land in", where "points" come from Closer's own weighted scoring of match events (fouls, throw-ins, saves, ...). No other venue lists anything comparable, so there is no second leg to arbitrage against; (b) trading is session-authenticated (Google login + embedded wallet) against an operator-run LMSR on a custodial-style balance, with no signed-order or API-key path documented, and the Terms prohibit "unauthorized automation"; (c) the US, UK, France, Australia, Belgium, Singapore and others are geo-restricted; (d) liquidity is thin per market (LMSR b = 2,000 USDC per 5-minute window) and the whole venue has done about $0.75M lifetime volume; (e) no docs, no audit, no published reserves, and Closer or affiliates take the other side of user trades.

## 2. Kind and market model

- **Kind:** onchain-other, "live-sports precision markets" on Solana. In practice a hybrid: off-chain operator-run LMSR matching engine, USDC held in a Solana program vault, per-fill settlement recorded on-chain (see sections 3, 5). (H for the pieces, M for the overall characterisation.)
- **Market unit = one "Market Window"** of a live match: football = a 5-minute slice (18 windows per 90 minutes, `minutes-1-5` ... `minutes-86-90`); cricket = one over (`innings-1-over-3`; 28-38 windows per T20). Each window has exactly one market `marketKey: "points-band"`, `marketType: "sports-fast-market-points-band-v1"` with **four mutually exclusive point ranges** (categorical / scalar-bucket, not binary). Example football ranges: `0-6, 7-12, 13-19, 20+`. Ranges are re-set per window "to reflect the match phase" (settled labels seen: `0-4`, `9-14`, `17+`, `0-5`, `19+` ...). Exactly one range pays. (H: General Market Rules; API `fast-markets/{id}` and `/rules`)
- **Scoring is Closer's own weighted event count** (H, `GET /fast-markets/530/rules`, rulesVersion `2026-10-07-b2000-ml1500`): goal 10, red card 10, yellow card 6, corner 5, penalty 5, shot on target 5, save 4, foul 2, throw-in 1. Cricket: runs in the over plus 5 per wicket (H: Market Rules text, not re-checked against an API rules payload). **The public General Market Rules page lists different weights** (goal 10, shot on target 3, corner 2, shot off target 1, yellow 1, save 1; default ranges `0-1, 2-3, 4-6, 7+`), so the written docs are stale or generic; the per-market `/rules` endpoint is authoritative ("market-specific rules ... priority 2").
- **Pricing contract `lmsr-fixed-point-v2`** (H, field `pricingContractVersion`). I verified it numerically on market 530: with liquidity parameter b = 2,000 (`liquidityParameterAtomic 2000000000`, 6 decimals), virtual quantities 0 / 34.17 / 0 / 166.07 shares, `p_i = exp(q_i/b) / sum_j exp(q_j/b)` gives 0.24368 / 0.24788 / 0.24368 / 0.26477, matching the API `lastPriceAtomic / probabilityScale` to 6 digits. So `lastPriceAtomic` values are a clean probability simplex (sum 1). Config also carries `feeBps 150` and `overroundBps 400` (a 4% overround on quotes; exactly how it is applied to executable prices is NOT FOUND, the quote endpoint is authenticated). `costBasisAtomic` 2,823.83 USDC (about b*ln4 = 2,772.6 plus seeded virtual shares; M). Each window therefore has a house-funded depth of about $2k with max-loss about $2.8k per window.
- **Tokenisation:** none in the usual sense. Positions are shares (1 share pays 1 USDC if its range wins) held as balances in Closer's ledger, not SPL tokens. API order fields are `outcomeIndex`, `side` (buy/sell), `sharesAtomic`; `quantityAtomic` per outcome is returned in the market snapshot. No outcome mint addresses appear anywhere (NOT FOUND: app JS, API, DefiLlama adapter). (H for the absence in the surfaces I read, L for "none exists on chain")
- **Order types:** market-style only: buy exact shares with `maxCostAtomic`, or sell shares with `minProceedsAtomic`, plus `deadlineAtMs` and an `idempotencyKey`. No resting limit orders / no order book. Min buy spend 1 USDC, max 10,000 USDC per order (`immediateOrderLimits` 1,000,000 / 10,000,000,000 atomic). (H, JS + market snapshot)
- **Timing is pre-event, not in-play on the scored window.** Calls close ("freeze") at roughly the moment the scored window starts: for market 530 (key `minutes-86-90`, title `85:00-90:00`) `sequenceStart clock-ms:4860000` (81:00 match clock) to `sequenceFreeze clock-ms:5160000` (86:00), actual `freezesAtMs 1791665145503`, and the timeline's first event-time estimate for the window starts at 1791665145000. `endsAtMs` (1791664200000) equals the scheduled kickoff + 90:00, i.e. a scheduled-clock figure, not the true end; labels and keys differ by one minute (85:00 vs 86). So key off `freezesAtMs` / `sequence*` fields, never `endsAtMs`, and do not assume wall-clock alignment between venues. (H for fields, M for interpretation)

## 3. Chains and collateral

- **Chain: Solana mainnet only** (H: app config `VITE_SOLANA_CLUSTER = mainnet-beta`; DefiLlama chains `["Solana"]`). **Collateral: USDC** only (H: market `currency: "USDC"`, 6 decimals; Risk Disclosure section 7 and DefiLlama adapter "USDC-only"). No EVM presence found.
- **Program:** `CLoseukDtTCoUe5ECMjiLABYTCtC94qJz9LpN8tSHPM4`, described by DefiLlama as the "Closer prediction-market vault program (Anchor), USDC-only" (M: from the third-party adapter, `dexs/closer/index.ts`; Closer's own site and bundle never print a program id). Instructions/events referenced: `settle_fill` (args: `fill_id`, `strike`, `size`, `price`, `gross_amount`, `side`, `stake`) and a `FillEvent` (wallet, market, strike, size, price, gross, fee, side, ts, version). "fee is ceil(gross * fee_bps / 10000) on BUY and 0 on SELL, computed on-chain; fee_bps is set per market at creation" (M, adapter comments). I did not verify the program on an explorer (WebFetch cannot render explorers and I did not POST JSON-RPC); IDL, source and audit are NOT FOUND (searched: GitHub code and repo search, web search for the id, DefiLlama `audits: "0"`).
- **Custody model (H/M):** Terms section 6: "Digital Assets committed to markets may interact with Solana programs or program-controlled escrow ... Not every interface action is necessarily an individual on-chain transaction." The app has a per-user "free balance" (`GET /fast-market-account/balance`; error code `INSUFFICIENT_FREE_BALANCE`), Solana deposit intents (`/deposits/solana/intents`), Halliday on-ramp intents (`/deposits/halliday/intents`) and custody withdrawals (`/fast-markets/custody/withdrawals`). So users deposit USDC into the vault, trade against an off-chain ledger, and fills are later submitted to the program via `settle_fill`. (H for endpoints, M for the sequencing)
- Wallets: Google login, then "Phantom Connect", "MetaMask Embedded Wallets" (Web3Auth Sapphire, Solana namespace) or external Phantom/MetaMask wallets (H: Terms 6, Privacy 5, app config).

## 4. Read API (classification: `unofficial-only`; no published API docs or terms)

## 5. Trade path and PayBox reachability

- **Programmatic trading: not offered.** The only trading interface is the app's session-authenticated REST API (`POST /fast-markets/{id}/trades/preview` then `/trades`; body per client code: `outcomeIndex, side, buyMode: EXACT_SHARES, sharesAtomic, maxCostAtomic | minProceedsAtomic, deadlineAtMs, idempotencyKey`; 200 = filled, 202 = pending, poll `trade-commands/status`) (H for the paths and field names from JS; never called). Auth is a bearer/session token obtained by Google login via Web3Auth/MetaMask Embedded Wallets (token refresh logic and `closer:user:<wallet>` SSE channel with `token` in the query string) (H). **No wallet-signed order, no API key, no public SDK** (NOT FOUND: JS, Terms, sitemap, GitHub).
- **PayBox reachability: no (for trading).** A PayBox Solana wallet could in principle send USDC to a deposit address returned by the authenticated `/deposits/solana/intents` call, but an agent cannot get a trading session without a human Google/Web3Auth login, there is no transaction-proposal route for placing or cancelling orders, EVM chains are irrelevant (Solana-only), and the Terms ban unauthorized automation. Funding-only is possible, trading is not. Any live test would also need the operator's location checked against the restricted list (section 8). (H for the facts, M for "not feasible")

## 6. Fees (H unless noted)

- **1.5% "taker fee on the executed transaction amount"** for any immediately executed transaction (Terms 9; `feeBps: 150`), paid by the trader, "no maker fee". The minimum/maximum call "fee included". The on-chain adapter comment says the fee is charged on **BUY fills only** (SELL = 0), whereas the Market Rules say exit "may incur the taker fee" (M conflict; the on-chain behaviour is more reliable). DefiLlama fees through 2026-10-17: $5,077 on $353,247 volume (1.44%, consistent with fee on BUY legs only) (H).
- **Quote overround 400 bps** (`overroundBps`) is an additional spread on the four prices (M on mechanics). LMSR price impact on top: with b = 2,000 and window volumes of $4-6k on the biggest matches, a few hundred dollars moves the price materially.
- Third-party deposit/withdrawal costs (Halliday, network fees) apply separately (Terms 9, 7). Welcome bonus $50 non-withdrawable credit; referral $10; the 1.5% fee still applies to bonus-funded trades (Promotions Terms).
- All-in round-trip friction for a taker: about 1.5% + part of 4% overround + price impact. Fees are retained 100% by the protocol treasury, no LPs (H: DefiLlama methodology).

## 7. Resolution mechanism and dispute risk

- **Operator-resolved from a sports-data feed.** "Closer uses the official competition record where reasonably available and may use a recognized sports-data provider"; market-specific rules name the controlling source (H: Market Rules 10). Image CDN and event-id formats in the API point to **Sportmonks** as the data provider (`cdn.sportmonks.com`, `providerEventId` strings) (M; Closer never names it in docs). Final points total and winning range are posted per window (`resolution.winningOutcomeKey`, `result.score`, `settlementState: confirmed`) with an on-chain proof link "when available" (H).
- **Operator discretion is large (H, Market Rules 12-14):** Closer may correct a provisional result before settlement, void a window (abandonment, unreliable data, "ranges fail to cover the valid outcome", suspected manipulation, "obvious error"), and cancel/correct trades it considers obvious errors. Voids refund principal and Closer's fee; network fees may not be recovered. Of 93 completed fixtures, many windows are voided (e.g. fixture 59 cricket: 8 voided vs 27 resolved; football fixtures show 2-15 voided windows in the early test days; later fixtures show 0-1) (H, `windowCounts`).
- **Dispute process:** "View result" flow or support@closer.market; no external arbiter, no bonded oracle, no on-chain dispute window. "Once a valid settlement is finalized on-chain, it is final except where the applicable smart contract expressly permits remediation." Complaints acknowledged within 5 business days, substantive response in 30 days (H).
- **Latency/stale-feed risk:** server time governs; feed states "delayed", "stale" (calls suspended), "under review" (calls paused), "interrupted/postponed/abandoned" (void+refund) are modelled in the client (H). Terms prohibit "exploit[ing] delayed sports feeds, data-source errors, software defects or stale quotes in bad faith" - i.e. latency arbitrage against Closer is explicitly a conduct violation.
- **Counterparty risk:** Closer, affiliates or "independent automated systems" take the other side of user positions; no audit published (DefiLlama `audits: "0"`); the Transparency page says Closer "does not publish reserve, audit, uptime or volume statistics" (H).

## 10. Event overlap with other venues (what matters for arbitrage)

- **Direct overlap: none.** Underlying fixtures (Premier League, La Liga, Serie A, ...) are the same matches that Polymarket, Kalshi, Limitless, Azuro, etc. list as match-winner / total-goals / props, but Closer's contracts pay on a proprietary weighted points total over a 5-minute window (H: rules). No other venue I know of lists "points range for minutes 36-40"; nothing can be hedged one-for-one. Even reproducing the underlying events elsewhere (goals, cards, corners in a minute range) is not possible with the foul/throw-in/save/shot-on-target components.
- **Possible signal use only (L/speculative):** Closer's live prices and the `latestEvent`/`livePoints` feed carry real-time match-event and tempo information (cards, goals, shots) from the provider; the fixture list is a clean mapping of kickoff times and Sportmonks team ids that could help entity-linking sports markets across venues. Neither is arbitrage.
- Sports only; no politics, crypto, macro.

## 11. Shared liquidity

- **Independent** (own LMSR per window, house/affiliate-funded, USDC in Closer's own vault). It does not route through or share books with Polymarket, Kalshi, Azuro or others. (H for LMSR + vault, M for "nothing shared": no integration language anywhere.) Third parties it depends on: Sportmonks (M), Halliday (deposits/routing), Phantom/MetaMask/Web3Auth, Helius RPC - none provide liquidity.

## 12. Adapter priority: skip

Reasons: no hedgeable overlap with other venues (the main point); trading not automatable and prohibited by Terms; heavy geo-exclusion; young, unaudited, custodial-style, operator-resolved; low liquidity. If the project wants a catalogue/signal entry later, a P2 read-only adapter is cheap: poll `/fast-fixtures?status=upcoming|ongoing`, then `/fast-markets/{id}` per open window, or subscribe to `GET /stream?channels=closer:fast-lobby` (SSE). Price conversion: `p = lastPriceAtomic / probabilityScale` (1e9); `volumeAtomic` / 1e6 = USD.
