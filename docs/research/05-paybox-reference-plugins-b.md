## 0. What matters most (read this first)

1. **A plugin cannot get an off-chain signature.** [H] The only things a plugin can return to PayBox are three `io.paybox/transactionProposal` kinds: `evm` (one unsigned call), `solana` (one unsigned tx) and `x402` (a USDC payment to an HTTPS URL on Base/Solana). "Unknown fields are rejected." There is no typed-data or message kind. So XO order signing cannot be a plugin proposal.
2. **Sign-then-submit works only as agent-orchestrated prepare -> core `request_wallet_sign` (typedData) -> submit.** [H docs for the tool; M live demo] `request_wallet_sign` accepts `op: typedData` (EIP-712) and returns a signature. One live-on-Base-mainnet reference implementation exists (Ghost Mode, `Himess/ghost-mode-paybox`): plugin tool `ghost_prepare` returns typed data + `human_summary`, the agent calls PayBox `request_wallet_sign`, then plugin tool `ghost_submit` sends the signature to the project's own HTTPS service. The author states it ran on mainnet 2026-10-17 (tx hashes in README; I could not verify on-chain because the block explorers were Cloudflare-challenged, and I did not bypass that).
3. **Autonomous grants do not auto-sign plugin proposals, but do auto-sign `request_wallet_sign`.** [H docs] "plugin money tools always pause for the user's approval, even under an autonomous grant." In contrast `request_wallet_sign` under an autonomous grant goes straight to `pending_signature`. Consequence: a $10-per-order cap in plugin code is advisory for off-chain orders, because the agent can sign any typed data without passing through the plugin. Enforce caps where the agent cannot skip them (the component that holds the XO API credentials and submits the order).
4. **Per-user secrets cannot live in a PayBox plugin.** [H] Env vars are plugin-wide and "non-sensitive"; secrets are host-scoped brokered headers the plugin code cannot read, and they are static per host (cannot compute a per-request HMAC). Every repo that needs per-user secrets either passes the secret through the agent as a tool argument (Ladder `errand_key`, Ghost `ghost_key`) or keeps state on its own server keyed by the paying wallet. XO's private endpoints need a per-user HMAC triplet (M, from an independent XO TUI client), so a relay service is the likely shape.
5. **No PayBox plugin in the ecosystem trades on an authenticated off-chain order book.** [M] The only "CLOB" plugin (`owenrobn/paybox-kreopoly-lens`, Polymarket) has a `place_bet` tool whose own source says the calldata is a "v0.1 placeholder"; Polymarket is otherwise read-only (Echo Markets, Second Opinion, Hedge) or on-chain redeem only (Foresyte). Nothing targets XO. So XO order flow would be a first.
6. **Chain 3223 is unproven.** [H/M] Docs: "the selected network must be available in PayBox." Live evidence of PayBox-signed plugin proposals exists for Base, Solana and (author-reported) Arbitrum One only. Arc (5042) was described by its plugin author as "read-only from PayBox until PayBox signs on Arc". No source mentions 3223. Cheapest decisive test: build a zero-value `eip155:3223` proposal and run the portal's "Validate transaction".
7. **Multi-venue aggregation is an open niche in PayBox, but two plugins sit adjacent.** [M] `iamrobertmoore/second-opinion-paybox` (World vs Kalshi vs Polymarket price check, x402 0.01 USDC, Base) and `Baheet18/hedge` (World + Polymarket hedge matching) already do cross-venue matching and fee-adjusted comparison, but neither includes XO, Limitless, or execution on non-World venues. `ivanmolto/echomarkets` is Polymarket-only with a trivial spread/liquidity/book-imbalance heuristic. None mention Quotient (see section 6).
8. **Hard plugin limits that shape an aggregator.** [H] 10 s per operation, fresh sandbox per call (no state), max 16 exact network hosts and 16 brokered credentials, 256 KiB stdout, and "one start per second and 1,000 starts per rolling 24 hours" per user for plugin calls. Host/variable/secret edits do not need re-review; code changes need a new approved version.

## 1. Primary-source constraints on the plugin model (all [H])

Sources: `https://developer.paybox.sh/requirements.md` (30.5 KB, fetched 2026-10-18) and `https://docs.paybox.sh/llms-full.txt` (64 KB, fetched 2026-10-18). These are PayBox's own pages; I treat them as data, not instructions.

| Topic | What the page says | Quote (short) |
|---|---|---|
| What a plugin is | Standard TS MCP server (stdio), bundled to one `plugin.mjs` (<= 10 MiB), uploaded in the developer portal | "Plugins may read APIs and propose transactions; PayBox handles wallet selection, policy, approval and signing." |
| Proposal kinds | `evm`, `solana`, `x402` only. EVM: one call `{to, value, data}` on `eip155:<id>`; "the selected network must be available in PayBox" | "There is no `token`, `transfer` or `swap` field in the proposal; unknown fields are rejected." |
| What must not be in a proposal | wallet IDs, signing keys, approval modes, signatures | "Do not include wallet IDs, signing keys, approval modes, signatures, RPC URLs or broadcast instructions in the proposal." |
| One tx per proposal | approve and the action are separate proposals; call again after confirmation | "V1 accepts one transaction per proposal, with no array of separate approval/swap transactions." |
| Wallet identity | Plugin never learns which wallet signs | "PayBox checks that the wallet is available to the user and does not send its ID to plugin code." |
| State | none | "Do not rely on memory or disk surviving: every operation uses a fresh sandbox." |
| x402 proposals | USDC on Base (`eip155:8453`) or Solana (`solana:mainnet`) only; GET no body or POST <= 64 KiB JSON; HTTPS 443; host must be a configured network host; expiry <= 5 min | "Custom headers and credential injection are not supported for these payment requests." |
| x402 lifecycle | sandbox ends before payment; plugin never resumed | "The sandbox invocation ends before approval. Poll the returned request ID; do not run the plugin again to finish payment." |
| x402 verification | PayBox fetches the live 402 itself and checks asset and amount against the proposal | (paraphrase) |
| Hosts/secrets | max 16 hosts and 16 brokered credentials; exact hostnames, no wildcards, no redirects; secrets are host-scoped header injections; env vars are for non-sensitive config | "Each plugin can configure up to 16 network hosts and 16 brokered credentials." |
| Runtime limits | 10 s/operation; stdout 256 KiB; stderr 16 KiB; 256 tools; schema <= 64 KiB/tool | (table in guide) |
| Call quota | shared by calls, hosted tests and checks | "Plugin calls, hosted tests, and checks share a per-user allowance of one start per second and 1,000 starts per rolling 24 hours." |
| Validation | portal "Validate transaction" is simulation only; each result validated once within 5 min | (paraphrase) |
| EVM refresh | PayBox refreshes nonce and rechecks execution before signing; EVM proposals do not raise approved fee limits | (paraphrase) |
| Tx window | shows raw calldata, no decoded summary | "It does not provide a decoded ERC-20 transfer, allowance or swap asset-change summary." |
| Remote plugins | one sentence mentions "remote plugins use their connected origin" for x402 hosts; nothing else documented | NOT FOUND beyond that sentence (searched `requirements.md`, `skill.md`, `llms-full.txt` for "remote") |
| Autonomy vs plugins | plugin money tools always pause for approval | "plugin **money tools always pause for the user's approval**, even under an autonomous grant." (`llms-full.txt`, Plugin tools section) |
| Off-chain signing | `request_wallet_sign` intents: `message`, `typedData`, `transaction`, `authorization`, `solanaMessage`, `solanaTransaction`, `raw`; autonomous -> `pending_signature`; the signing window (or an SDK `pbxk1.` key) signs | "Wallet signing never happens in agent code." |
| Cross-chain | `request_swap` has `dst_chain` (different chain = bridge; `pending_settlement` while in flight) | (docs table) |
| Chain catalogue caveat | `discover_tokens mode:"chains"` lists featured networks incl. Robinhood, Arc, Hyperliquid | "Catalog membership does not guarantee provider coverage or trading support." |
| Headless SDK | `PayboxClient.requestWalletSign({credentialId, intent})` "signs in-process when a pbxk1. signing key is configured"; personal `pbx_live_*` API keys work as bearer | (docs) |

Note the ambiguity: "pause for the user's approval" may mean a passkey step-up or an in-window confirm; docs do not say which for plugin proposals. [H that the sentence exists; unresolved which mode.]

Note a staleness data point: the Aug 2026 Hermes repo lists a `world_find_markets` tool and PayBox MCP tools `moonx_resolve_binding` / `submit_envelopes`; by Oct 2026 Second Opinion and Hedge use `world_search`, `world_get_events`, `world_get_markets`, `world_orderbook`, and the current PayBox tool list I can see has no `submit_envelopes`. So the Hermes headless-signing recipe is partly stale. [M]

### 2.7 `kinnuworks/ladder` (no license file, created 2026-10-17, pushed 2026-10-17; Solidity + TS + Next.js)
"Give your AI a budget, not your card": one PayBox approval funds an on-chain **errand account** (CREATE2 clone) that can release each step's cap, once, to a one-time key that pays a service over x402, then refunds the rest to the owner. Layout: `contracts/` (Foundry: `Errand.sol`, `ErrandFactory.sol`, unit/fuzz/invariant/fork tests), `plugin/` (7 tools: `ladder_plan`, `ladder_fund`, `ladder_step`, `ladder_check`, `ladder_status`, `ladder_finish`, `ladder_refund`; modules `core.ts`, `rails.ts`, `x402.ts`, `plan.ts`; `test/{core,rails,steps,interop}.test.ts`), `web/` (relayer + funding endpoint), `docs/{SPEC,RAILS}.md` (35 KB rail integration notes, including live unpaid x402 probes of three services).
- (i) **Off-chain signatures, done without PayBox signing them**: the errand is an ERC-1271 contract; its session key (held by the plugin/agent) signs EIP-3009 `transferWithAuthorization` messages, a Merkle-committed step list limits what the contract will validate, and Ladder's relayer submits. Step keys sign x402 payments themselves (`signAsRunner`). The single PayBox approval is an **x402 proposal to Ladder's own funding endpoint** (`POST /api/fund`) whose 402 `payTo` is "a pure function of the terms in the body". Lesson: an x402 proposal *is* a PayBox-signed EIP-3009 authorization plus an HTTP POST with a JSON body (<= 64 KiB), usable to deliver USDC plus a parameter payload to a server in one approval, Base/Solana only.
- (ii) **Per-user secret = the "errand key"** (`ldr1_...`): the plugin is stateless, so the key (session seed + step keys + brief) is returned to the agent and must be passed back on each call; the README concedes "It is still a secret. Anyone who gets it can spend what the errand still holds". Escape hatch needing no key: `ladder_refund` (owner calls `refund()` from their wallet). Plugin "bundle never reads environment variables"; constants are baked in by `scripts/set-deployment.mjs`.
- (iii) hard budget cap ($1-$100), per-step caps and expiry enforced **by the contract**, owner-only refund paths; before proposing, the plugin fetches the 402 itself and refuses unless `payTo` equals the errand address it computed and the amount equals the budget (`fundingProblem`); `checkChallenge` rejects an unexpected payee or an amount over the step cap; call windows (9-18 local); text refused if it "looks like a key". Relayer abuse limits derive a **daily cap from public chain history** (`web/lib/limits.ts`: relayer nonce now minus nonce 24 h ago), which is a stateless daily counter.
- (iv) heavy x402 usage both as buyer (StablePhone, PostalForm, Mosbie; x402 v1 and v2 handled in `readChallenge`) and seller (`/api/fund`). RAILS.md notes that a static payTo allowlist works for two rails but PostalForm issues a per-order payTo, so it binds order -> payTo -> amount.
- (v) none. (vi) mocked-network unit tests (`steps.test.ts` fakes Base RPC, relay, StablePhone, PostalForm), `core.ts` drift check in CI, Foundry fuzz/invariant/fork tests (real Base USDC), and `interop.test.ts` against a local **anvil fork** (gated by `LADDER_INTEROP`).
- **Reuse:** YES, high value: payee/amount pre-check of a 402 before proposing; "untrusted_service_output" labelling; stateless daily-cap-from-history trick; mocked-world unit test harness; anvil-fork interop test. Caution: key-in-conversation design is exactly what our plan wants to avoid.

## 9. Design implications for our plan

1. **Architecture:** thin Open Plugin + our own HTTPS relay (one exact host) that holds per-user XO API credentials (derived through XO's ClobAuth flow, signed by the PayBox wallet) and performs the submit. Plugin tools: public reads direct from the venues; `xo_prepare_order` (returns typed data + `human_summary` + HMAC `quote_id`); `xo_submit_order` (takes signature + `quote_id`, relay recomputes digest, recovers signer, enforces caps, POSTs). Funding / approvals / redeem use real EVM proposals (always human-approved).
2. **Blind signing risk:** the signed object is the Kernel `hash` wrapper (opaque bytes32). Rely on the plugin's `human_summary` and the relay's digest re-derivation; do not assume the PayBox window will show the order. Check how PayBox renders `Kernel{hash}` (Ghost's author flagged the same open item).
3. **Caps:** per-order cap in `xo_prepare_order` AND in the relay; per-day and per-market-creation counters in the relay (or derived from XO order history); grant policy `value_cents` where supported; use a dedicated low-balance PayBox wallet. Do not rely on PayBox approval for off-chain orders under an autonomous grant.
4. **Do not make `request_wallet_sign` the only barrier**: the agent can sign and post an XO order itself if it has API creds. Keeping creds only in the relay (not in agent context) is what actually enforces the cap.
5. **Chain 3223 first test:** zero-value `eip155:3223` EVM proposal -> portal "Validate transaction". Only if that fails, evaluate the raw-tx fallback (P24).
6. **Aggregator read layer:** Polymarket Gamma/CLOB/Data API, Kalshi v2 markets (no auth), XO data/order-book API, within 16 hosts; design batch tools (one call returns many quotes) because of 1,000 calls/day and 1/s; mark every venue string untrusted; add a rule-equivalence check before calling anything an arbitrage.
7. **Quotient:** ask the user for the product URL/API; plan for either an x402 proposal (Base/Solana USDC) or a brokered-header key; ensure host is allowlisted.
8. **Testing:** adopt the full ladder in section 5, plus recorded fixtures of XO and venue responses, a mocked-world suite for submit/relay, and an anvil/XO-testnet job for funding calls if the testnet RPC is reachable from CI.
9. **Skills:** ship a SKILL.md modeled on `paybox-x402-services` (cost-before-spend, never re-call a write, partial-success semantics).

Risks
- Hackathon repos are 1-3 days old; claims of mainnet success are self-reported and I could not independently verify any on-chain tx (explorers challenged curl; I did not bypass).

6. Is an externally hosted ("remote") plugin possible? One sentence in the guide implies it; nothing else documented.

### B. Corrected

**B1. "Autonomous grants ... do auto-sign `request_wallet_sign`" (section 0 item 3, gate 8, design implications 2-3) was tagged [H] but is only half of what the docs say.** `llms-full.txt` also says (Credential/Approval mode section): "Regardless of mode, **sensitive operations** (revealing a raw secret, signing, issuing keys) require a fresh passkey assertion", and line 24/32/90 say "behind a passkey for anything sensitive" / "Above-threshold and sensitive operations always pause for a passkey". Against that, `Allow (autonomous)` says wallet signs "move to `pending_signature`", the `request_wallet_sign` tool says "`pending_signature` - autonomous: the signing window can sign right away", and the SDK section says "the operation clears immediately under an autonomous grant" (with a `pbxk1.` key). Corrected text: *"Docs are internally inconsistent on whether an autonomous grant signs `request_wallet_sign` without a passkey. Treat 'agent can sign any XO order typed data unattended' as UNVERIFIED and design for both outcomes; plugin/relay-side caps remain the only enforceable cap either way."* Also note that even on the autonomous path a signing window (host UI) or an SDK `pbxk1.` key is needed to produce the artifact, so a headless OAuth-only agent cannot sign.

**B2. "plugin money tools always pause for the user's approval, even under an autonomous grant" (gate 8: "Autonomous grants do not auto-sign plugin proposals") is real text, but its scope is narrower than used.** It sits in the "Plugin tools" section of `llms-full.txt`, which defines plugins as "**first-party plugins** - batches of extra tools (e.g. prediction-market or spot-market access) a user switches on from the app's Plugins screen". `requirements.md` (the Open Plugin guide) never says Open Plugin proposals always need a passkey; it says "Review the details and approve when required" and "PayBox handles wallet selection, policy, approval and signing". Corrected: [H] sentence exists; [L] that it governs third-party Open Plugin proposals; the question "do autonomous grants auto-sign plugin proposals" is UNANSWERED, not "answered-go".

**B3. XO signature prefix.** Section 2.13 says the owner signature "is prefixed `0x00`" (from `xo-market-tui` `src/trading/signing.ts`, which does return `0x00` + 65-byte signature). XO's own docs (https://docs.xo.market/guides/smart-accounts#xo-smart-account-signatures and the `smart_wallet_api_key.ts` example) specify the wire signature as `0x01 || bytes20(<Kernel v3 ECDSA validator address>) || ecdsa(wrappedDigest)` (86 bytes), with `KERNEL_V3_VALIDATION_TYPE_VALIDATOR = 0x01`. [H, XO primary docs]. Do not copy the TUI's `0x00` prefix; the third-party client is a non-authoritative example. (The wrapped digest itself, domain `Kernel` / `0.3.1` / chainId 3223 / verifyingContract = smart account, struct `Kernel(bytes32 hash)`, matches XO docs, so PayBox `typedData` can in principle produce the same 65-byte ECDSA; sibling note 01 covers this.) The L1 ClobAuth digest is wrapped the same way (domain `ClobAuthDomain`/`1`/3223 with no verifyingContract), and the L1 headers also include `XO_NONCE`.

**B4. HMAC canonical string.** Section 2.13 says the L2 HMAC covers `timestamp + METHOD + path(+query) + body`. Precisely: the TUI supports two modes, `path-only` (its default, labelled "Live XO compatibility") and `path-with-query` (labelled "Documented form"); XO's docs (guides/smart-accounts, "L2 HMAC") say `timestamp + method + path-with-query + body`, URL-safe base64 HMAC-SHA256, timestamp within +/-30 s. Live behaviour vs docs therefore disagrees; a relay must test both against a real key before relying on either. Also XO's `POST /auth/api-key` page names the response header `POLY_API_KEY`/`POLY_PASSPHRASE` while the guide and TUI use `XO_API_KEY`/`XO_PASSPHRASE` (XO docs inconsistency; verify live).

**B5. "No PayBox plugin ... trades on an authenticated off-chain order book" (section 0 item 5, summary fact, NOT FOUND list) is true only for third-party Open Plugin repos and should be scoped that way.** PayBox's docs describe first-party plugins for World (prediction markets; tools include an orderbook and buy; "geofenced World money tools") and Hyperliquid (an order-book venue; `paybox hyperliquid` command group removed in SDK 1.0.0 in favour of `paybox plugins`). Their source is not public, so how they sign and submit is UNKNOWN; they are at least an existence proof that PayBox's own plugins reach order-book venues. A third-party capture of the World contract (see C2) shows the Solana-based World market is reached through DFlow, not an authenticated CLOB with API keys, so World is not a counterexample to "authenticated CLOB with per-user HMAC"; Hyperliquid is unverified either way.

**B6. Hermes `submit_envelopes` / `moonx_resolve_binding` "appear removed" (sections 1, 2.4, risks).** `llms-full.txt` says: "The internal `submit_*` / `moonx_*` tools the window uses are hidden from the model and are not part of this surface." So they are hidden/internal and unsupported, not necessarily removed. The recommendation (do not depend on them) stands.

**B7. Ladder `limits.ts` (section 2.7, P17).** The "daily cap from public chain history" counts the *relayer's own* transactions (nonce now minus nonce a day ago) to protect the relayer's gas; per-IP and per-instance counters are in-memory and not shared. It is not a per-user counter. Adapting it to "orders per day per user" needs per-address history (e.g. XO order history), not a nonce delta.

**B8. "no wildcards or redirects" (section 1 table).** `requirements.md` says "wildcards, redirect chains and arbitrary destinations are not a networking contract". That is not an explicit ban on a single redirect; `redirect: "error"` in Undertow/AgentPress is a defensive choice. Keep it as a recommendation, not a documented rule.

**B9. World tool names are not purely second-hand.** The notes say World tool names are only second-hand (six names). A third-party repo, `a040900/world-pm-public-observer` (docs/research/2026-10-01-world-mcp-readonly-verification-r0.md and `evidence/.../mcp-receipts.json`), preserves `get_contract(paybox://plugins/world)` output; the names present are `world_buy_outcome`, `world_change_position`, `world_filter_outcome_mints`, `world_get_events`, `world_get_markets`, `world_market_prices`, `world_orderbook`, `world_positions`, `world_redeem`, `world_search`, `world_search_results` (M: third-party capture of a first-party contract, dated 2026-09-30/10-01; the get_events/orderbook tools were annotated read-only, buy/change/redeem state-changing). The NOT FOUND about `moonpay/paybox-plugin` still holds (its tree has 9 blobs including `.gitignore` and `LICENSE`, not 8).
